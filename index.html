About

A software engineer and bioinformatician working for two science technology platforms at The Francis Crick Institute in London.

I like working on scientific systems or supporting systems that make science easier, more reproducible, faster, or more accurate. Coming from a biological background, I enjoy problems where understanding the underlying biology is important but where a big impact can be made with better software or computational solutions.

I have a wide range of experience, having worked on cross-platform desktop applications, web applications, data processing pipelines, iOS apps, long-running jobs on HPC clusters, and Linux servers for hosting applications.

I like working on problems with tight constraints, like limited RAM or strict speed requirements. I find these push you towards more interesting solutions and give you more freedom to experiment. Optimisation is another of my favourites, both at the architecture level and in lower-level changes. The fast feedback loop and measurable results can make it almost game-like.

In data analysis, much of my focus is on scientific correctness and minimisation of errors. That includes the misuse of statistical significance, data leakage from batch correction and imputation, and how results are interpreted.

Over the last year, I've been enjoying the transition to working with agentic AI. I've curated skills, built workflows to benchmark agents and run automated adversarial reviews in which agents use the apps themselves to check that changes work, and found ways to increase my output responsibly.

In my free time, I like to make things that solve problems and experiment with things I haven't done before. I've created iOS apps for myself and my friends, I've recently been setting up my own home server, and I built CrimeMapsUK, a web app for the public to explore the full UK policing dataset (updated monthly).

MANIC Live

Python, PySide6, NumPy, SciPy, SQLite2023-now

  • Python rewrite of MATLAB software for GC-MS isotope-tracing experiments: it reads raw instrument files, extracts a chromatogram for each target metabolite, corrects for natural isotope abundance and calculates calibrated amounts.
  • Sole developer since the rewrite began in 2024. I've maintained the MATLAB version, which had become slow and hard to extend, since 2023.
  • Work alongside the scientists on the platform to decide what to build and fix next, and improvements are tested before release. Other labs send bugs and requests through GitHub issue forms.
  • Used for all GC-MS work on the platform, cutting a typical analysis from around two weeks to a couple of hours. It's open source and also used by other labs at the Crick, Imperial College London and elsewhere around the world. A paper describing it is in preparation.
  • Added chromatographic peak deconvolution, which fits peak shapes to separate overlapping signals, and an unlabelled mode that checks each compound's identity using qualifier ions, retention time and ion ratios.
  • Added manual peak review: reviewers accept or reject peaks from the plot grid, and every export records the MANIC version, settings and reviews behind it, so results can be traced back.
  • Moved the data out of memory into a local SQLite database, with a schema that stores raw and corrected chromatograms separately and indexes them by compound and sample, so large datasets run on ordinary lab PCs.
  • Pages now usually render in about 0.2 seconds, against up to 15 seconds in the MATLAB version: chromatograms and isotope corrections are calculated once at import and stored, plotting is vectorised, and deconvolution fits are cached.
  • Built a benchmark suite on synthetic GC-MS data with planted hard cases, which times every change and checks its peak areas against the previous version. It lets me hand optimisation work to AI coding agents and reject what they get wrong.
  • 411 tests cover the maths, data import and interface logic, and GitHub Actions builds the Windows and macOS installers for each release.

Metabolomics analysis pipeline Live

Python, R, limma, scikit-learn, Streamlit2025-now

  • A Python and R package for metabolomics studies, taking raw instrument exports through to differential abundance and predictive models. It grew out of a one-off analysis for another project in 2025, and I'm its sole developer.
  • Standardised the metabolomics platform's data analysis, for clinical and research studies with drift correction, QC filtering and leak-free validation built in. A new study needs a layout file and a config, not new code.
  • Used so far to analyse three large clinical cohort studies with manuscripts in progress and currently being benchmarked on public studies.
  • Every pull request gets an automated AI review on a self-hosted runner which builds the environment, runs the tests, uses the GUI in a browser to check changes end to end, and follows skills curated for reviewing scientific code.
  • 643 tests, all on synthetic or public data, so no patient data enters the repository.
  • Every scientific choice has a decision page citing its evidence, a checker confirms each citation still matches, and each run records its config, input hashes, git commit and R and limma versions.
  • AI agents working in the repository must follow the decision pages and pass the checker, so their changes can't quietly alter the science.
  • Imports raw XLSX or CSV exports into one validated dataset format, then corrects instrument drift against QC samples, filters imprecise features and checks each batch's design before any analysis runs.
  • Runs limma differential abundance alongside logistic regression, PLS-DA, random forest, and supports XGBoost and MLP models. Held-out scores come with 95% intervals and an optional permutation test.
  • Imputation, scaling and tuning are fitted inside subject-grouped training folds only, so held-out scores stay honest. A simulation in the docs shows why, with leaky feature selection scoring an AUC of 0.98 on pure noise against 0.50 done properly.
  • A local browser GUI walks scientists through import, design check, run and results.

CrimeMapsUK Live

Django, PostGIS, Celery, Redis, Stripe, JavaScript2026-now

  • A site I built and run on my own: free maps, dashboards and pages for police force areas and 1,398 postcode districts in England and Wales, built from around 70 million published UK police records.
  • Started to see what I could do with the data: friends moving house couldn't get a clear picture of local crime, and police data is public but hard to interpret on its own.
  • Over 3,000 visitors and 6,000 page views since analytics began in July 2026, currently around 800 visitors a month.
  • Crime map tiles are served straight from PostGIS as vector tiles over pre-aggregated hexagon summaries, so there's no separate tile server.
  • New police data is ingested twice a month on a timer: each month is replaced cleanly, the summaries are rebuilt, and every run is logged.
  • Paid PDF reports for a postcode, from £9.99 through Stripe checkout and generated in the background.
  • The reports are built for accuracy: they state the exact area and date range, compare it with the police force area and the national pattern, use aggregated maps rather than exact-looking pins, explain the data's limits (approximate locations, published outcomes only, reporting gaps) and show no per-resident rate without an official population figure.
  • One Hetzner server runs Nginx, Gunicorn, PostGIS, Redis and Celery, with Tailscale for admin access and automatic deploys when I push to GitHub.
  • Server-rendered Django with vanilla JavaScript and no build step, with 378 Django tests and 44 deployment tests.

Study onboarding agent In development

Python, Docker2026

  • A test harness for whether an AI coding agent can safely write the converters that bring new public metabolomics studies into an analysis pipeline.
  • Built around the mistakes that fail silently: a sample ID 01 read as 1, a missing value written as below the detection limit, a batch column filled in when the study recorded none.
  • Each attempt runs in a sandbox with no network and is judged by checks the agent never sees, including a prompt-injection case.
  • Each run records everything needed to reproduce its result without calling the model again.
  • In the first evaluation, six runs across three public studies, every converter matched the reference on every cell, and the agent's own tests caught 32 of 48 planted bugs.
